# 提 PR 对抗审查

效果对标：对着 diff 拆台，不是实现者再写一遍自检清单。

## 何时用（强制）

在以下动作**之前**必须跑完本技能，未通过不得声称「行为不变 / 可合入 / 兼容」：

- 准备开 PR / 推送会更新 PR 的 commit
- 回应 review 后宣称已修好
- 热部署或发布前声称与已审查版本行为一致

触发信号（命中任一即用）：改了共享协议或合同面、多入口复用同一路径、错误降级路径、文档或配置声明支持一组变体（枚举、scheme、flag、后端）。

## 禁止

- 用实现者自己的 happy path 代替本轮
- 只输出备忘录式清单而不读真实 diff、不找具体漏洞
- 自己审自己且不换审查视角（必须另起一轮拆台身份）

## 步骤

### 1. 冻结审查输入

收集：

- 相对基线的完整 diff
- 声称的意图一句话
- 文档或配置里**声明支持**的变体列表

### 2. 换身份拆台（核心）

另开审查轮（优先：多模型对抗，见 `interrogate`；至少：独立子代理只读 diff）。审查者**不是**实现者。

审查提示必须覆盖（可改写，不可删意）：

1. diff 引入或改动的行为，是否还有**姐妹实现**仍用旧假设？
2. 声明支持的每个变体，新路径是否真的走到同一语义？哪个变体会失败或换路？
3. 错误时是否**静默降级**？表面成功会不会掩盖换路？
4. 现有测试是否只证明成功路径、证明不了「走了对的分支」？

审查者必须给出：具体文件与符号、如何复现或证明、严重度。禁止空泛「注意边界情况」。

### 3. 裁决

按发现分类：

- **必须修**：正确性 / 安全 / 静默换路 / 姐妹路径合同破裂。作者若声称「行为不变」而声明变体未齐步，把「声明不成立」单独列为必须修，不要并进姐妹路径条目里含糊带过
- **该修**：可维护性、可测性缺口
- **可记下**：风格与题外话

有「必须修」则 **阻塞提交或更新 PR**，先改再重跑本技能。

### 4. 结构优先于清单

若根因是双份实现：先合并到共享 helper，再补会失败的测试锁住「支持的变体不得静默换路」。不要只追加文档矩阵。

### 5. 交卷格式（给用户看）

短输出即可：

- 意图一句话
- 拆出台的发现（无则写「对抗审查未发现必须修项」，并写查了哪些姐妹路径或变体）
- 是否允许开或更新 PR

交卷时写清：哪些声明变体在哪些入口上语义一致、哪些分叉。多数变体仍一致而某一变体单独分叉时，点名该变体，不要笼统说「行为有变」。

## 完成标准

- 存在一轮独立于实现者的 diff 审查记录
- 声明支持的变体与姐妹路径被点名检查过
- 无未关闭的「必须修」
- 若声称行为不变：有分支可区分的证明，不是成功状态码 alone
